# W-23296072 — Toggle filters: independent local/org visibility controls

## Context

- Package: `salesforcedx-vscode-org-browser`
- Replace cyclic viewMode with 2 independent toolbar toggles (show-local, show-org)
- Top-level types filtered at `getChildren(!element)` based on:
  - showLocal OFF → hide types where project ComponentSet has no local files of that xmlName
  - showOrg OFF → hide types that exist ONLY in the org (i.e., present in describe result but NOT in local ComponentSet)
- Filter state: `workspaceState` keys `orgBrowser.showLocal` / `orgBrowser.showOrg`
- Context keys: `sf:orgBrowser.showLocal`, `sf:orgBrowser.showOrg`, `sf:orgBrowser.hasOrgData`
- Org toggle disabled until first type expansion populates org data (hasOrgData = false initially)
- Auto-migrate legacy `orgBrowser.viewMode` → booleans on activation
- Icons: `resources/{dark,light}/cloud-on.svg` (toggle visual); use codicon `$(eye)`/`$(eye-closed)` for local toggle

## Filter semantics (corrected)

The root `getChildren(!element)` path currently calls `describe()` to get all org metadata types and maps them to tree nodes. It does NOT fetch a ComponentSet. The filters work as follows:

- **showLocal ON, showOrg ON** (default): show all types from describe (current behavior).
- **showLocal OFF**: fetch ComponentSet at root level via `yield* api.services.ComponentSetService.getComponentSetFromProjectDirectories()`. For each type from describe, check if the ComponentSet contains components of that xmlName (using `getComponentFilenamesByNameAndType` or iterating `getSourceComponents`). Hide types that have zero local components. This means "I only want to see types that exist in the org" — hide types that also happen to be local-only.
- **showOrg OFF**: hide types that exist ONLY in the org describe result but have no local representation. Fetch ComponentSet at root level. Build a set of xmlNames present in ComponentSet. Hide types from describe whose xmlName is NOT in the local ComponentSet set. This means "I only want to see types I have locally" — the tree becomes a local-only view.
- **showLocal OFF AND showOrg OFF**: show types present in BOTH describe AND local ComponentSet (intersection).

Summary: Both filters require ComponentSet at root level. The describe result provides org types; the ComponentSet provides local types. Each toggle independently removes one "source" of types from the visible set.

## Phases

### Phase 1 — Add showLocal/showOrg state + filtering to MetadataTypeTreeProvider

Files:
- `src/tree/metadataTypeTreeProvider.ts`

Work:
- Add `showLocal: boolean` and `showOrg: boolean` fields (default both true)
- Add `private _hasOrgData = false` field with a public getter and a `setHasOrgData(v: boolean)` method
- Add setters for showLocal/showOrg that update field + fire `_onDidChangeTreeData` event
- In root `getChildren` (no element), after building type nodes from `describe()`, apply filters:
  ```typescript
  // Fetch ComponentSet at root level when either filter is active
  const needsComponentSet = !this.showLocal || !this.showOrg;
  const projectComponentSet = needsComponentSet
    ? yield* api.services.ComponentSetService.getComponentSetFromProjectDirectories()
    : undefined;
  ```
  - When `projectComponentSet` is available, build a `Set<string>` of xmlNames that have local components (iterate `projectComponentSet.getSourceComponents()` and collect their `type.name` values)
  - showLocal OFF: keep only types whose xmlName IS in the local types set (hide types with zero local components)
  - showOrg OFF: keep only types whose xmlName IS in the local types set (hide org-only types that have no local files)
  - Both OFF: intersection — keep only types present in both describe AND local ComponentSet
- In the type expansion path (`element.kind === 'type'`, line 94-104): after a successful `listMetadata` call, if `_hasOrgData` is false, set `_hasOrgData = true` and call `vscode.commands.executeCommand('setContext', 'sf:orgBrowser.hasOrgData', true)`. This is the concrete hook mechanism — it fires inline in the existing Effect chain, no separate EventEmitter needed.
