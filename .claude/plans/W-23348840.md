# W-23348840 — Replace core ChannelService w/ services ChannelService

## Context

- Target: `packages/salesforcedx-vscode-core/src/channels/index.ts:11-12`
  - `const OUTPUT_CHANNEL = vscode.window.createOutputChannel(nls.localize('channel_name'))`
  - `export const channelService = new ChannelService(OUTPUT_CHANNEL)` (utils-vscode `ChannelService`)
- **Bug this fixes = dupe channel.** `buildAllServicesLayer(ctx, nls.localize('channel_name'))` (index.ts:42) → `ChannelServiceLayer(displayName ?? fallback)` (`effect-ext-utils/src/allServicesLayer.ts:36`) creates its own `'Salesforce CLI'` OutputChannel. core displayName=`'Salesforce CLI'` (package.json), channel_name msg=`'Salesforce CLI'` (messages/i18n.ts:18) ⇒ **2 same-named channels** (VS Code doesn't dedupe by name).
- Services `ChannelService` (`salesforcedx-vscode-services/src/vscode/channelService.ts:14`) = `Effect.Service`, not `new`-able w/ an OutputChannel; API = Effect-valued `getChannel`/`showChannel`/`clearChannel`/`appendToChannel`. Owns the channel via infinite `Cache` keyed by name (L65).

### Precedent = org pkg (same epic)

- Org already solved identical dupe: commit `9d270ed84`. Pattern in `salesforcedx-vscode-org/src/channels/index.ts`:
  - drop module-level `new ChannelService(createOutputChannel(...))`
  - keep legacy utils-vscode `ChannelService` **wrapper** over the ONE Effect-layer-owned channel
  - `setOrgChannel(channel)` wires wrapper at activation; `getOrgChannelService()` accessor (throws if pre-wire)
  - activation (`org/src/index.ts:74-76`): `const orgChannel = yield* (yield* api.services.ChannelService).getChannel; setOrgChannel(orgChannel); ctx.subscriptions.push(orgChannel)`
  - `api.channelService = getOrgChannelService()` built AFTER `activateEffect` (index.ts:61)
- Mirror exactly for core. Keeps consumer shape (utils-vscode `ChannelService`) intact while backing it w/ the single services channel.

### Consumers of exported `channelService` instance (must stay working)

1. `metadataSupport/metadataXmlSupport.ts` — `channelService.appendLine(...)` ×8 (sync). Called from `initializeProject` (index.ts:91).
2. `index.ts` `api.channelService` (public API; type `channelService: typeof channelService`, index.ts:191). External type consumer: `salesforcedx-vscode-apex-debugger/src/utils/coreExtensionUtils.ts` imports `SalesforceVSCodeCoreApi` but only reads `.telemetryService` — **no external `.channelService` read** (repo grep clean). Shape unchanged anyway ⇒ safe.
- NOT in scope: `commands/aliasList.ts`, `commands/configList.ts` already use `api.services.ChannelService` (services shape). Untouched.

### Timing constraints

- `api.channelService` currently built in `activate()` (index.ts:44) BEFORE `activateEffect` runs (L58). Lazy accessor throws pre-wire ⇒ **must build api after activateEffect** (org ordering).
- `activateEffect` has `internalDev` early-return (index.ts:77-80) before `getServicesApi` (L83). metadataXmlSupport skipped in that path, but external `api.channelService` still exposed ⇒ **wire channel BEFORE the internalDev branch**. Fetch the channel right after L66, before the internalDev return.

### No new activation dependency for internal-dev users (adversary follow-up)

- **Wiring the channel before the internalDev return does NOT widen the services-extension dependency.** Internal-dev activation already hard-depends on the services extension today:
  - `activateEffect` L66 `yield* ensureCurrentWorkingDirIsProjectPath()` ⇒ `workingDirectory.ts:19` `yield* (yield* ExtensionProviderService).getServicesApi` — runs BEFORE the internalDev branch (L77). Any `ServicesExtensionNotFoundError`/`InvalidServicesApiError` there already rejects `activate()` (no catch around `getRuntime().runPromise(activateEffect(...))`, index.ts:58) for internal-dev users too.
  - core `package.json` `extensionDependencies: ["salesforce.salesforcedx-vscode-services"]` ⇒ VS Code activates services before core activates at all; `getServicesApi` (extensionProvider.ts:32) can't hit the "briefly unavailable" case the finding posits.
- So the added `const coreChannel = yield* (yield* servicesApi.services.ChannelService).getChannel` reuses an already-resolved dependency; it introduces no new failure surface for `sf:internal_dev`. Plan states this explicitly rather than silently reordering.
- Reuse the same `servicesApi` binding for both the channel fetch and the later `ProjectService.isSalesforceProject()` (don't fetch twice).
