# W-24264945

## Context

- Stop shipping `@salesforce/templates` inside `salesforcedx-vscode-core`.
- Core `esbuild.config.mjs` copies `@salesforce/templates/lib/templates` into `dist/templates` (package `node_modules`, else repo-root `node_modules`). `packaging.assets` includes `dist`, so the core vsix ships that tree.
- Services copies an allowlist (`packages/salesforcedx-vscode-services/esbuild.config.mjs:35-48`), not the full `lib/templates` tree core copies (`packages/salesforcedx-vscode-core/esbuild.config.mjs:42-44`, `:58-59`). Desktop reads services `dist/templates` from disk.
- `@salesforce/templates@66.16.0` `lib/templates` also has `digitalexperiencesite`, `flexipage`, `lightningout`, `lightningtest`, `uiBundles`, `uiembedding`. None are in the services allowlist. `TemplateOptionsFor` still names `LightningTest` and `UIBundle` (`packages/salesforcedx-vscode-services/src/core/templateService.ts:57-68`); no in-repo `TemplateType.LightningTest` / `TemplateType.UIBundle` caller.
- Dropping those 6 dirs from every vsix is intentional. This WI does not widen the services allowlist to match the old core tree.
- Runtime create is unaffected: `getTemplatesRoot` reads `salesforce.salesforcedx-vscode-services` + `dist/templates` (`templateService.ts:122-130`, `:211-213`), never the core extension.
- Core `package.json` `dependencies` do not list `@salesforce/templates`. No core TS import of it.
- Approach: delete the core copy. Services stays the only extension that bundles the allowlisted assets.
