# W-23514880: Harden O11yReporter telemetry sends

## Goal

Prevent failures from `@salesforce/o11y-reporter` event sends and final flushes from escaping `O11yReporter`, without changing successful telemetry or batching behavior.

## Scope

- Production change: `packages/salesforcedx-utils-vscode/src/telemetry/reporters/o11yReporter.ts`
- Test coverage: `packages/salesforcedx-utils-vscode/test/jest/telemetry/reporters/o11yReporter.test.ts`
- No dependency, batching, App Insights, navigator shim, or other telemetry changes

## Applicable Skills

- `typescript`: preserve repository TypeScript style and existing comments; use a module-level `const` arrow function.
- `verification`: run package-focused tests plus repository readiness checks after implementation.

## Phase 1: Contain O11y Failures

1. Add a module-level `guard(label, op)` helper after the imports. Catch synchronous errors, log `O11yReporter <label> failed:` with `console.error`, and return normally.
2. Wrap the standard event `logEvent` call with `guard('logEvent', ...)`.
3. Keep command PFT delivery asynchronous, but attach a rejection handler that logs `O11yReporter sendPftEvent failed:`. This contains dynamic schema-load failures and synchronous `logEventWithSchema` throws converted to rejections by `sendPftEvent`.
4. Wrap the exception event `logEvent` call with `guard('logEvent(exception)', ...)`.
5. Await `forceFlush()` with a rejection handler that logs `O11yReporter forceFlush failed:` so `dispose()` resolves after flush failure.
6. Preserve automatic batching setup, shutdown-hook behavior, event payloads, and existing batching comments.

## Phase 2: Prove Failure Containment

1. Extend the existing reporter Jest suite using its mocked `O11yService` instance.
2. Make `logEvent` throw and assert `sendTelemetryEvent()` returns without throwing.
3. Make `logEvent` throw and assert `sendExceptionEvent()` returns without throwing.
4. Make `forceFlush` reject and assert `dispose()` resolves.
5. Spy on `console.error` in failure tests to suppress expected test output and verify the operation-specific diagnostics.
6. Retain existing happy-path assertions as regression coverage for transparent guards.

## Verification

1. Run the focused Jest file with the package Jest config.
2. Run `npm run test -w @salesforce/salesforcedx-utils-vscode`.
3. Run `npm run lint -w @salesforce/salesforcedx-utils-vscode`.
4. Run `npm run compile` from the repository root because package-only compilation is not sufficient for completion.
5. Allow repository readiness hooks to run compile, lint, tests, bundle, Effect checks, and knip; resolve all failures attributable to this change before reporting readiness.
