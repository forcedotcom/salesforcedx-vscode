# W-23348834 — Replace hasRootWorkspace w/ services WorkspaceService

## Context

- Sole `hasRootWorkspace()` call in apex pkg: `packages/salesforcedx-vscode-apex/src/languageUtils/languageClientManager.ts:271` (WI cites 280; actual 271), inside `removeApexDB()`.
- `removeApexDB` = plain async; guard `if (hasRootWorkspace() && vscode.workspace.workspaceFolders)` then reads `workspaceFolders[0].uri`, deletes `.sfdx/tools/<NNN>` dirs.
- `hasRootWorkspace` impl = `Boolean(ws?.workspaceFolders?.length)` (`salesforcedx-utils-vscode/src/workspaces/workspaceUtils.ts:10`). Only import from `@salesforce/salesforcedx-utils-vscode` in file (line 8).
- Services equivalent: `WorkspaceService.getWorkspaceInfo()` → `{ uri, isEmpty, ... }`; `isEmpty = !folders?.length` (`salesforcedx-vscode-services/src/vscode/workspaceService.ts:37`). Non-empty ⇒ `!isEmpty`. (`isNonEmptyWorkspace` not exported → use `!isEmpty`.)
- Access pattern (same file's sibling + `languageServer.ts:261`): `const api = yield* (yield* ExtensionProviderService).getServicesApi;` then `yield* api.services.WorkspaceService.getWorkspaceInfo()`; run via `getRuntime().runPromise(...)`.
- `getRuntime` from `./services/runtime`; `ExtensionProviderService` from `@salesforce/effect-ext-utils`. Neither yet imported in languageClientManager.ts.
- Prefer `info.uri` over `vscode.workspace.workspaceFolders[0].uri` once info in hand (drops 2nd vscode guard, matches services intent).

### New failure channels vs. the old pure check (must handle)

- Old `hasRootWorkspace()`: synchronous `Boolean(...)` — never throws. Rewrite adds 2 typed errors on `getServicesApi` step: `ServicesExtensionNotFoundError | InvalidServicesApiError` (`effect-ext-utils/src/extensionProvider.ts:20-25`); unhandled ⇒ `getRuntime().runPromise(...)` rejects.
- `getWorkspaceInfo` itself CANNOT fail: it's an `Effect.fn` over `Effect.sync` (`workspaceService.ts:30-73`); error channel is `never`. Only `getServicesApi` needs a catch. (`getWorkspaceInfoOrThrow` — which can fail `NoWorkspaceOpenError` — is NOT used here; we use `getWorkspaceInfo` + `info.isEmpty`.)
- Blast radius if it rejects: `removeApexDB` is awaited at `languageClientManager.ts:235` (`await this.removeApexDB();`) OUTSIDE any try/catch, and BEFORE the `setTimeout` block whose `finally` resets `this.isRestarting = false` (lines 243-263). A rejection propagates out of `restartLanguageServerAndClient`, stranding `isRestarting === true`, so every later restart short-circuits at the "already restarting" guard (204-207) until window reload.
- Fix = defense in depth (both layers):
  1. In-effect no-op catch mirroring `languageServerOrphanHandler.ts:133-140`: `.pipe(Effect.catchTags({ ServicesExtensionNotFoundError: () => Effect.void, InvalidServicesApiError: () => Effect.void }))`. ⇒ error channel = `never` — no services extension ⇒ skip DB cleanup, like the old guard returning `false`. (No workspace/`isEmpty` already returns early inside the gen.)
  2. Call-site guard: wrap `await this.removeApexDB();` in try/catch (log via `console.log`, swallow) so ANY unexpected defect/rejection still can't strand `isRestarting`. Matches the pre-existing swallow-and-continue posture of the inner fs-delete try/catch.
