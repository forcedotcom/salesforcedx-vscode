# W-23498957: Route Apex Debugger telemetry through Effect spans

## Context

- `packages/salesforcedx-vscode-apex-debugger/src/index.ts` still obtains core's frozen `telemetryService` for debugger metrics, activation, and deactivation.
- `SEND_METRIC_EVENT` originates in the separate `salesforcedx-apex-debugger` adapter process and reaches the extension host through a DAP custom event. Keep that bridge unchanged; replace only the extension-host telemetry sink.
- ADR-0012 requires new telemetry to use spans, while ADR-0006 directs consumers away from the core extension API.
- The debugger already builds `AllServicesLayer`, owns a managed Effect runtime, and depends on `salesforcedx-vscode-services`; core is not needed after the telemetry calls are removed.
- `package-lock.json` records the debugger's core workspace devDependency and must change with the manifest.
- `@salesforce/core` usage in `isvContext.ts` and `bootstrapCmd.ts` remains out of scope.

## Approach

Use the existing Apex Debugger Effect runtime for all 3 observability paths. Emit `apexDebuggerMetric` as a top-level span whose attributes preserve the adapter event body's `subject` and `type`; retain the current activation span and add a matching deactivation `Effect.fn`. Then remove the obsolete core wrapper and every debugger package/test dependency on core.

## Phases

1. **Route lifecycle and metric telemetry through Effect**
   - Update `packages/salesforcedx-vscode-apex-debugger/src/index.ts`.
   - Keep `SEND_METRIC_EVENT`, `isMetric`, and `vscode.debug.onDidReceiveDebugSessionCustomEvent` as the adapter-to-host boundary.
   - In the validated metric branch, run an `apexDebuggerMetric` `Effect.withSpan` through `getRuntime()`, with the actual adapter body fields (`subject`, `type`) as attributes and top-level export semantics. Do not retain the current `any` cast to nonexistent nested `properties`/`measurements`.
   - Remove the core telemetry import, activation `initializeService`, and deactivation `sendExtensionDeactivationEvent` call.
   - Keep `activateEffect` as `Effect.fn('activation:salesforcedx-vscode-apex-debugger')`. Add an exported `Effect.fn('deactivation:salesforcedx-vscode-apex-debugger')` and have `deactivate` await it through the managed runtime, preserving the existing activation/deactivation console messages.
   - Delete `packages/salesforcedx-vscode-apex-debugger/src/utils/coreExtensionUtils.ts`; this removes the package's `SalesforceVSCodeCoreApi` type consumption.

2. **Remove core from the debugger package graph**
   - Update `packages/salesforcedx-vscode-apex-debugger/package.json` to remove `salesforcedx-vscode-core` from `devDependencies`, `salesforce.salesforcedx-vscode-core` from `extensionDependencies`, and the core compile/package targets from the `compile` and `test:desktop` Wireit dependency lists.
   - Keep `salesforcedx-vscode-services` in `devDependencies`, `extensionDependencies`, bundle/test dependencies, and desktop fixtures because it provides `SdkLayerFor` and the services API.
   - Update the debugger entry in `package-lock.json` to remove only its core workspace devDependency.
   - Update `test/playwright/fixtures/desktopFixtures.ts` so `additionalExtensionDirs` contains only `salesforcedx-vscode-services`; correct the adjacent comment.

3. **Remove obsolete Jest setup**
   - Update `test/jest/activation.test.ts` in a test-only phase after the source phase.
   - Remove the deleted `coreExtensionUtils` import/mock, telemetry initialization setup, and `initializes telemetry` assertion.
   - Retain command-registration coverage and the minimal VS Code registration stubs.
   - Add no new test in this source migration: repository verification guidance permits touching `/src` and `/test` together only for imports/renames, and this test edit is the required cleanup for the deleted import. Validate span behavior through compile, Effect diagnostics, and existing span-export infrastructure.

4. **Verify repository readiness**
   - Confirm no `getTelemetryService`, `coreExtensionUtils`, `SalesforceVSCodeCoreApi`, or `salesforcedx-vscode-core` reference remains under `packages/salesforcedx-vscode-apex-debugger`.
   - Confirm the `salesforcedx-apex-debugger/src/adapter/apexDebug.ts` `Event(SEND_METRIC_EVENT, ...)` producers are unchanged and `@salesforce/core` imports remain untouched.
   - Run the debugger Jest suite, including the retained activation command-registration coverage.
   - Run `npm run compile -w salesforcedx-vscode-apex-debugger`, `npm run lint -w salesforcedx-vscode-apex-debugger`, `npm test -w salesforcedx-vscode-apex-debugger`, `npm run vscode:bundle -w salesforcedx-vscode-apex-debugger`, and `npm run vscode:package:legacy -w salesforcedx-vscode-apex-debugger` from the repository root with Wireit caching disabled where applicable.
   - Do not add a separate Playwright run: the fixture edit only removes an extension no longer declared or consumed, and Apex Debugger is outside the verification skill's required Playwright package list. Existing debugger desktop suites continue loading services.
   - Run `npm run check:dupes` and inspect changed-file findings.
   - Require repository readiness hooks to pass compile, lint, Effect diagnostics, unit tests, VS Code bundle, and knip before implementation is reported ready.
