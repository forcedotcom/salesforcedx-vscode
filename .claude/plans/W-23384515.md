# W-23384515 — Wire display-language into i18n so JA bundles resolve

## Context

- JA path DEAD today: 16+ pkgs register `jaMessages` but every runtime resolve = en. `loadMessageBundle()` reached only arg-less via `LocalizationService.nls` getter → `DEFAULT_LOCALE`.
- No `setActiveLocale`/`getActiveLocale`; no `env.language` refs anywhere. First place locale gets wired.
- Locale session-constant in VS Code (display-language change reloads window → re-`createNls`). Resolve once at nls construction, store on service instance. No active-locale singleton, no cache invalidation.
- i18n lib is vscode-free, also runs in node LSP procs (aura/lwc language servers) where `vscode` module absent → lib MUST NOT import vscode.
- Locale sources:
  - Node (desktop host + spawned LSP): `process.env.VSCODE_NLS_CONFIG` JSON `.locale` (lowercased). Set by VS Code. No consumer wiring. (ref: vscode-nls `src/node/main.ts`)
  - Web host: no `process.env` (web bundle injects empty process polyfill, `scripts/bundling/process-polyfill.js:5`). Only `vscode.env.language`, passed explicitly by web-targeted extensions.
- Verified vs develop: `nlsFactory.ts` `createNls` no locale param; `advancedLocalization.ts` `LocalizationService` ctor/getInstance no locale, nls getter calls `loadMessageBundle()` arg-less; `Locale = 'en'|'ja'` (`types/localization/config.ts`); jest vscode mock `env` (`config/__mocks__/vscode.js:127`) lacks `language`; eslint rule `noInlineEsbuildPlatform` requires inline `process.env.ESBUILD_PLATFORM` comparison (no var/destructure). All wired `messages/index.ts` (6 extensions + effect-ext-utils/core/lightning) call `createNls` w/o locale today. NOTE: shared libs (effect-ext-utils, core, lightning) DO import vscode in their extension-host code and ARE bundled (not externalized) into web consumers — earlier assumption they never load vscode was wrong (see Phase 2).
- Non-breaking: all new params optional; external npm consumers (`@salesforce/vscode-i18n`, versionedIndependently) keep resolving en.

## Phases

### Phase 1 — lib: locale resolution API
Files:
- `packages/salesforcedx-vscode-i18n/src/envLocale.ts` (new): `parseNlsLocale(raw?: string): Locale | undefined`. try/catch `JSON.parse(raw ?? '{}')`, read `.locale`, return only if `LocalizationConfig.getInstance().isLocaleSupported(value)` else `undefined`. Never throws.
- `src/i18n/advancedLocalization.ts`: add optional `locale?: Locale` to private ctor + `getInstance(instanceName, locale?)`; store `private readonly locale`. nls getter: `loadMessageBundle(this.locale ? { locale: this.locale } : undefined)`. Singleton = first getInstance wins (later same-name calls ignore locale arg). Only validated locales stored → no Config type assertion.
- `src/nlsFactory.ts`: add optional `locale?: string` to `CreateNlsOptions`. Resolve once: `const fromEnv = process.env.ESBUILD_PLATFORM !== 'web' ? parseNlsLocale(process.env.VSCODE_NLS_CONFIG) : undefined;` then validate `locale` param via `LocalizationConfig.getInstance().isLocaleSupported` (widen param to string, validate inside — `env.language` typed string, unsupported values like `de`/`zh-cn` fall back to base/en); `const resolved = validatedLocale ?? fromEnv;` pass to `getInstance(instanceName, resolved)`.
  - `ESBUILD_PLATFORM !== 'web'` MUST be inline in ternary (eslint `noInlineEsbuildPlatform`; ADR 0013). Web esbuild `define` collapses branch → tree-shakes `process.env` read from web bundles. Node LSP: `ESBUILD_PLATFORM` undefined → `undefined !== 'web'` true → env read runs (correct).
- `src/index.ts`: export `parseNlsLocale` only if a test imports it directly (test imports from `../../../src/envLocale` → no index export needed).

Commit: `feat(i18n): resolve display-language from env + optional locale param - W-23384515`

### Phase 4 — e2e: prove JA renders in a real window (ADVOCATE FIX)
This WI's whole point is a previously-dead runtime path (JA actually rendering). Unit/bundle-grep prove resolution logic + bundle size, NOT that a running window shows a JA string. Add e2e for BOTH host targets.

Mechanism facts (verified, so specs assert the right thing):
- Web (`vscode.env.language`): web ext host sets `appLanguage = platform.language = getNLSLanguage() || 'en' = globalThis._VSCODE_NLS_LANGUAGE` (vscode `webWorkerExtensionHost.ts:205`, `platform.ts:106`). `@vscode/test-web` does NOT expose a locale option and never sets `_VSCODE_NLS_LANGUAGE` (no CLI/Options field — verified in `node_modules/@vscode/test-web`). Playwright context `locale` only drives `navigator.language` → web `_locale` (platform locale), NOT `env.language`. So a web spec sets `globalThis._VSCODE_NLS_LANGUAGE = 'ja'` in the page before the workbench reads it (`platform.ts` reads `getNLSLanguage()` at module load). Start with `page.addInitScript` before `page.goto('/')`; builder MUST confirm it wins over test-web's `nls.messages.js` script tag (which may reset the global) — if not, inject via a route/script that runs after that tag. The spec passing IS the proof the injection point is correct. Assert a known `jaMessages` label renders instead of English default.
- Desktop (`vscode.env.language`): equals `resolvedLanguage`, which is `'en'` UNLESS the JA language pack is installed (vscode `nls.ts` `resolveNLSConfiguration` — falls back to `resolvedLanguage:'en'` with no lang pack, even with `--locale=ja`). Since the 6 consumers pass `vscode.env.language` (param wins over env), a desktop spec on a wired consumer needs the language pack installed. `createDesktopTest` already supports `marketplaceExtensions` (`createDesktopTest.ts:130`) → add `MS-CEINTL.vscode-language-pack-ja` + `--locale=ja`. `--locale` is NOT currently threaded into `launchArgs` (verified: only `--user-data-dir`/`--extensions-dir`/dev-paths/`startupArgs`), so extend `CreateDesktopTestOptions` with an optional `locale?: string` in the shared `playwright-vscode-ext` fixture (add `${locale ? '--locale='+locale : ''}` to both `launchArgs` branches) rather than a per-package hack.

Specs to add:
- Web/headless: `packages/salesforcedx-vscode-metadata/test/playwright/specs/displayLanguageJa.headless.spec.ts`. `page.addInitScript` sets `_VSCODE_NLS_LANGUAGE='ja'` before `page.goto('/')`, run a command surfacing a metadata JA string (e.g. `delete_source_confirmation_message` → 'ソースファイルを削除...' or `confirm_delete_source_button_text` → 'ソースを削除'), assert the JA text renders (not the English). metadata already has 27 headless specs + JA bundle.
- Desktop: `packages/salesforcedx-vscode-metadata/test/playwright/specs/displayLanguageJa.desktop.spec.ts` (metadata has 3 desktop specs already). Fixture variant with `marketplaceExtensions: ['MS-CEINTL.vscode-language-pack-ja']` + new `locale: 'ja'`; assert a metadata JA command/label renders. This exercises the `vscode.env.language` param path end-to-end through the real desktop NLS pipeline (the `contributing/localization.md:143` `--locale=ja` verification, automated).
- If desktop language-pack install proves flaky/slow in CI, fall back to a second desktop spec on an UNWIRED consumer that exercises only the `VSCODE_NLS_CONFIG.locale` env path (`--locale=ja` alone resolves ja via `parseNlsLocale`, no lang pack needed) — but the web addInitScript spec is the primary must-have and is deterministic.
