# W-24703758 — Interactive Replay Debugger Breakpoint Metadata

## Context

- Replace Replay Debugger's legacy workspace-wide `debugger/lineBreakpoints` request with parser-backed, document-scoped TypeScript Apex Language Server metadata.
- Existing flow: `DebugConfigurationProvider` calls Apex extension `getLineBreakpointInfo()` once before launch, sends all workspace `LineBreakpointInfo[]` in launch args, then adapter validates DAP `setBreakpoints` from its launch-time maps.
- Legacy data shape: `{ uri, typeref, lines }`; lines are 1-based debugger lines. Adapter needs URI-to-lines for breakpoint verification and typeref-to-URI for replay-log source resolution.
- New debugger API from W-24375837 requires one canonical Apex document URI per call. It has 2 separate `workspace/executeCommand` commands:
  - `apex.debugger.lineBreakpoints` / `getLineBreakpointInfo(uri)` → executable source lines and type refs.
  - `apex.debugger.exceptionBreakpoints` / `getExceptionBreakpointInfo(uri)` → user and system exception metadata.
- The APIs were delivered together, but are not a combined request. This story consumes only line-breakpoint metadata. Exception breakpoint configuration is separate scope.
- Current `vscode.debug.onDidChangeBreakpoints` listener only maintains checkpoints. Add a separate listener for interactive source breakpoint metadata.
- Source edits during a session remain a concern, but this plan refreshes on breakpoint changes only. It does not add document-change invalidation.

## Preferred Behavior

1. User adds or changes a breakpoint in a supported Apex document.
2. Extension host requests parser-backed line metadata for that URI and replaces the host cache entry.
3. Before launch, host warms entries for existing Apex source breakpoints and passes a metadata snapshot to the adapter.
4. During an active `apex-replay` session, host sends URI-scoped updates to the adapter.
5. Adapter reconciles cached breakpoint validity and emits DAP breakpoint `changed` events for late metadata. It must not block `setBreakpoints` on cross-process LS work.
6. A first response without metadata is provisional/unverified; a later update can mark it verified.

## Phases

### 1. Confirm and expose typed document API

Commit: `refactor(apex): expose document breakpoint metadata API`

- Inspect the actual Apex extension API landed with W-24375837 before changing consumers.
- Require canonical URI input and typed line results; no raw command names or JSON-RPC from Replay Debugger.
- If the API is not exported by `salesforce.salesforcedx-vscode-apex`, add the smallest typed public method and consumer schema validation.
- Do not call `getExceptionBreakpointInfo` in this path.

### 2. Host-owned URI metadata cache

Commit: `feat(replay-debugger): cache line breakpoint metadata by URI`

- Add a Replay Debugger host-side module that owns document metadata.
- Key by canonical URI; retain complete line metadata for all outer and nested types in that document.
- Deduplicate concurrent fetches per URI.
- Replace one document entry without clearing entries for other documents.
- Expose: ensure metadata for URI set; snapshot cached entries; obtain one refreshed document result.
- Normalize VS Code source breakpoint URIs before API calls; filter unsupported files. Initial story scope: Apex classes. Confirm trigger inclusion before implementation.
- Keep exception metadata out of this cache.

### 3. Interactive pre-session updates

Commit: `feat(replay-debugger): refresh metadata on breakpoint changes`

- Register a second `vscode.debug.onDidChangeBreakpoints` listener during Replay Debugger activation; retain the checkpoint listener unchanged.
- Consider added and changed `vscode.SourceBreakpoint` entries. Removed-only entries need no fetch.
- Deduplicate affected Apex URIs per event and asynchronously ensure their metadata.
- Existing breakpoints before a debug session populate the cache for the next launch.
- Fetch failures leave existing cached metadata intact and log/surface a concise diagnostic without disrupting unrelated breakpoint operations.

### 4. Launch snapshot migration

Commit: `refactor(replay-debugger): launch from document breakpoint cache`

- Remove Replay Debugger use of the legacy workspace-wide Apex API.
- `DebugConfigurationProvider` enumerates current supported source breakpoints, warms missing cache entries, and passes the cache snapshot as launch metadata.
- Preserve adapter launch initialization and its synchronous DAP `setBreakpoints` validation.
- Keep replay-log source URI resolution working with cached typeref-to-URI entries plus existing Org Metadata Catalog fallback. Do not add a new workspace-wide fetch to resolve log sources.
- Migrate checkpoint upload to ensure metadata only for enabled checkpoint source URIs, reusing the host cache.

### 5. Running-session adapter updates

Commit: `feat(replay-debugger): reconcile live breakpoint metadata`

- Add a Replay Debug Adapter custom request for replacing one URI's line metadata.
- Extension host sends it only to active `apex-replay` sessions after a successful refresh; ignore other debugger types.
- Replace, never append, URI metadata in the adapter. Remove stale lines and typeref mappings belonging to that URI while preserving other documents.
- Refactor `BreakpointUtil.createMappingsFromLineBreakpointInfo()` into explicit full-snapshot and URI-replacement operations.
- Track requested DAP source breakpoints with stable adapter-issued IDs, source URI, client line, and current verification state.
- On a URI metadata update, recompute only that URI's requested breakpoint validity and executable breakpoint list.
- Emit DAP `breakpoint` events with reason `changed` for any validity transition. Do not wait for LS results inside `setBreakpoints`.

### 6. Tests

- Host cache: canonical URI calls, affected-file filtering, per-event dedupe, in-flight dedupe, replacement without cross-document clearing, and failed-refresh behavior.
- Breakpoint events: pre-launch additions/changes warm cache; removed-only events do not fetch.
- Launch: current Apex breakpoints are warmed and snapshot metadata reaches adapter; no legacy whole-workspace request.
- Adapter: initial snapshot validation; one-document replacement; stale mapping removal; unaffected URI preservation; provisional-to-verified and verified-to-unverified DAP `changed` events.
- Checkpoints: enabled checkpoint URIs are fetched through the cache; metadata failure preserves existing user-visible failure behavior.
- Integration: start a replay session, add a breakpoint in another unchanged Apex class, and confirm it becomes verified without relaunching.

## Decisions Before Editing

- Scope supported documents: classes only as named by W-24703758, or include triggers for parity with W-24375837.
- Confirm the exact custom request and DAP `BreakpointEvent` behavior supported by the adapter framework.
- Confirm handling of a language-server fetch failure while a valid cached entry exists: retain cache and log, or explicitly invalidate.
- Document edits during a running session: no automatic invalidation in this story; define follow-up behavior separately.
