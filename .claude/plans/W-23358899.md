# W-23358899 — [spike] POC: bundle Visualforce ext + LSP for VS Code Web

## Context

Spike. Prove VF extension runs on VS Code Web. Mirror `salesforcedx-vscode-lwc` web pattern, but fix LWC's anti-patterns in new code (don't copy verbatim).

Done when: ext activates on web AND 1 real LSP feature (completion) works on `.page` AND Playwright web spec verifies. Deliverable: go/no-go + confirmed pattern. Spike is NOT a ship — the `browser` field must not reach customers in this WI.

Current state (all node-only):
- `salesforcedx-vscode-visualforce/esbuild.config.mjs` — only node builds (`dist/index.js`, `dist/visualforceServer.js`).
- `src/startLanguageServer.ts` — `Effect.fn`, `vscode-languageclient/node`, IPC transport, `documentSelector` scheme hardcoded `file`; color provider scheme `file`.
- `package.json` — no `browser`, no `packaging`/`packageUpdates` block, no `activationEvents`, no `test:web`; `vscode:package` = plain `vsce package` (reads local manifest directly → whatever is in `package.json` ships).
- LS `salesforcedx-visualforce-language-server/src/visualforceServer.ts` — `createConnection()` + `vscode-languageserver/node`; `onInitialize` builds `getLanguageModes(...)` synchronously.
- `modes/languageModes.ts:35` — static top-level `import { getJavascriptMode } from './javascriptMode'`; `javascriptMode.ts` statically imports `typescript` (`sys`, `getDefaultLibFilePath`, node fs). Runtime `supportedLanguages['javascript']` flag only guards the *call*, not the import.

LWC reference pattern (adapt, do not copy blindly):
- client split: `src/languageClient/{index,node,web}.ts`, branch `process.env.ESBUILD_PLATFORM === 'web'`; web = `Worker` + `vscode-languageclient/browser`; node = IPC.
- server split: browser overrides `createConnection` w/ `BrowserMessageReader/Writer(globalThis)`; entry branches on ESBUILD_PLATFORM.
- esbuild: `commonConfigBrowser` from `scripts/bundling/web.mjs`; server IIFE `format:'iife'`, `platform:'browser'`, `define ESBUILD_PLATFORM='web'`.
- e2e: `playwright.config.web.ts` (`createWebConfig`, `testIgnore:['**/*.desktop.spec.ts']`), `web/headlessServer.ts` (`createHeadlessServer`), fixtures branch desktop/web via `VSCODE_DESKTOP`.
- Deviations from LWC (required, see below): (a) web client factory fails with a `Schema.TaggedError`, not `throw new Error`; (b) `browser` field is gated, not shipped; (c) 1 cross-platform `.headless.spec.ts`, no desktop-only completion duplicate.

## Phases

### Phase 1 — LS browser connection + build-time dead-code elimination of `typescript`
Refactor `visualforceServer.ts`: branch `createConnection` on `ESBUILD_PLATFORM` — web uses `createConnection(new BrowserMessageReader(globalThis), new BrowserMessageWriter(globalThis))` from `vscode-languageserver/browser`; node keeps `createConnection()` from `/node`.

**Eliminate `typescript` from the web bundle at build time (not a Phase 3 escalation).** The runtime `embeddedLanguages.javascript=false` flag CANNOT drop `typescript` — the static import at `languageModes.ts:35` stays regardless, so esbuild bundles `typescript` (uses node `fs`, breaks web). Fix in `languageModes.ts`: remove the top-level `import { getJavascriptMode }` and load it behind the build-time literal `process.env.ESBUILD_PLATFORM !== 'web'` so esbuild's `define` collapses the branch and tree-shakes `javascriptMode` + `typescript` out of the web bundle:
```ts
if (supportedLanguages['javascript'] && process.env.ESBUILD_PLATFORM !== 'web') {
  const { getJavascriptMode } = await import('./javascriptMode.js');
  modes['javascript'] = getJavascriptMode(documentRegions);
}
```
Make `getLanguageModes` async as a result; `connection.onInitialize` in `visualforceServer.ts` may return `Promise<InitializeResult>` — await the modes there. Node build keeps JS mode (branch true); web build drops it (literal false → dead code).
- files: `packages/salesforcedx-visualforce-language-server/src/visualforceServer.ts`, `packages/salesforcedx-visualforce-language-server/src/modes/languageModes.ts`
- commit: `feat(visualforce): browser-compatible LS connection + web-safe embedded modes - W-23358899`

### Phase 2 — ext client platform split (Effect idioms, no `throw`)
Add `src/languageClient/{index,node,web}.ts`. `index.ts` dynamic-imports node/web on `ESBUILD_PLATFORM` (mirror LWC). web: `Worker(dist/web/visualforceServer.js)` + `vscode-languageclient/browser`, `embeddedLanguages.javascript:false` init opt. node: IPC → `dist/visualforceServer.js`.

**Do NOT copy LWC `web.ts`'s `throw new Error` on Worker-creation failure** (`salesforcedx-vscode-lwc/src/languageClient/web.ts:51`) — that violates `effect-best-practices` (FORBIDDEN: throw inside Effect flow; Errors must be `Schema.TaggedError`, not generic `Error`). Instead:
- Define `class LanguageClientWorkerStartError extends Schema.TaggedError<LanguageClientWorkerStartError>()('LanguageClientWorkerStartError', { serverPath: Schema.String, cause: Schema.Unknown })`.
- Web factory returns an `Effect` (VF `startLanguageServer` already `Effect.fn`).
- On `new Worker(...)` failure: `yield* Effect.fail(new LanguageClientWorkerStartError({...}))` — no `throw`.
- `startLanguageServer` handles it with `catchTag('LanguageClientWorkerStartError', ...)` (log to channel; LSP unavailable is non-fatal for the spike) — do NOT `catchAll`.
- Export the error type per `ts4023-effect-errors` so the `Effect.fn` return type names it in `.d.ts` (`export type { LanguageClientWorkerStartError }`).

Rework `startLanguageServer.ts` to call the platform `createLanguageClient`; broaden `documentSelector`+color provider schemes to `file`+workspace-folder schemes (memfs) — build the scheme set from `workspace.workspaceFolders` like LWC `web.ts:57-63`.
- files: `packages/salesforcedx-vscode-visualforce/src/languageClient/index.ts`, `.../node.ts`, `.../web.ts`, `src/startLanguageServer.ts`
- commit: `feat(visualforce): platform-split language client for web - W-23358899`

### Phase 3 — web esbuild + gated `browser` field
`esbuild.config.mjs`: add browser ext build (`commonConfigBrowser`, `external:['vscode']`, `entryPoints:['./out/src/extension.js']`, `outdir:'./dist/web'`) + browser IIFE server build (`format:'iife'`, `platform:'browser'`, `target:'es2020'`, `define ESBUILD_PLATFORM='web'`, `mainFields:['module','main']`, `outfile:'./dist/web/visualforceServer.js'`).

**Gate the `browser` field — must NOT ship to customers this WI.** VF's `vscode:package` is plain `vsce package`, which ships whatever top-level `browser` the manifest has. To keep e2e/`run:web` working (VS Code Web reads `browser` from the manifest at `extensionDevelopmentPath`) WITHOUT shipping it:
- Do NOT commit a top-level `"browser"` in `package.json`.
- Inject `"browser":"./dist/web/index.js"` into the manifest only for the spike, behind a build-time flag (e.g. a prebuild step gated on `process.env.VF_WEB_SPIKE`) consumed by `run:web`/`test:web`; the committed, ship-path manifest stays browser-less. The shipped VSIX (`vscode:package`) therefore does not enable web until the go/no-go WI adds it deliberately.
- Add `activationEvents:["onLanguage:visualforce"]`, add `../../scripts/bundling/web.mjs`+`fs-polyfill.js` to `vscode:bundle` wireit `files`.

Regression guard (not the place the `typescript` problem is discovered — Phase 1 already fixed it): `esbuild --metafile` assert `typescript` is absent from `dist/web/visualforceServer.js`. If present, Phase 1's dead-code elimination regressed — fix there, not by aliasing.
- files: `packages/salesforcedx-vscode-visualforce/esbuild.config.mjs`, `package.json`, prebuild flag script
- commit: `build(visualforce): gated web esbuild config + spike browser field - W-23358899`

### Phase 4 — Playwright web spec (single cross-platform LSP spec)
Add `test/playwright/playwright.config.web.ts` (`createWebConfig({testDir:'./specs'})` + `testIgnore:['**/*.desktop.spec.ts']`), `test/playwright/web/headlessServer.ts` (`createHeadlessServer({extensionName:'Visualforce', callerDirname:__dirname, additionalExtensionDirs:['salesforcedx-vscode-metadata']}`). Refactor `fixtures/index.ts` to branch desktop/web on `VSCODE_DESKTOP` (mirror LWC).

**Consolidate — do NOT add a desktop-only completion duplicate.** VF's `playwright.config.desktop.ts` has no `testIgnore`, so it picks up every `specs/*.spec.ts`; adding `visualforceLsp.headless.spec.ts` alongside the existing `visualforceLsp.desktop.spec.ts` `Autocompletion` test (line 79) would run the SAME `<apex:pageM`→`apex:pageMessage` assertion twice on desktop. Repo convention (`lwcLspAutocompletion.headless.spec.ts`) is ONE `.headless.spec.ts` asserting the behavior, run on both configs.
- Delete `specs/visualforceLsp.desktop.spec.ts`: its `Autocompletion` test moves into the new headless spec; its only other case (`Go to Definition`) is `test.skip`'d TODO (LS doesn't support it) — carry the skipped case into the headless spec as the documented gap, or drop it.

Runs on desktop config (no testIgnore for headless) AND web config.

Add `test:web`+`run:web` wireit (deps `vscode:bundle`, services/metadata `:vscode:bundle`, `playwright-vscode-ext:compile`); `run:web`/`test:web` set `VF_WEB_SPIKE` so the gated `browser` field is present.
- files: `packages/salesforcedx-vscode-visualforce/test/playwright/playwright.config.web.ts`, `.../web/headlessServer.ts`, `.../fixtures/index.ts`, `.../specs/visualforceLsp.headless.spec.ts` (new), delete `.../specs/visualforceLsp.desktop.spec.ts`, `package.json`
