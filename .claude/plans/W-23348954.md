# W-23348954 — Move code2ProtocolConverter to effect-ext-utils; migrate apex ChannelService; drop apex utils-vscode dep

## Context

Two independent moves + a dep drop:

1. **code2ProtocolConverter** — 3 near-identical copies:
   - canonical: `salesforcedx-utils-vscode/src/languageClients/conversion.ts` (exported `index.ts:27`); consumed by apex `languageServer.ts:9`, apex-replay `checkpointService.ts:13`
   - duplicate local const: lwc `clientOptions.ts:17` (never imported utils-vscode)
   - all 3 consumers already dep `@salesforce/effect-ext-utils` → move fn there, zero new consumer edges.
2. **apex ChannelService** — WI premise (WI9 precedent) was wrong: apex never migrated. `channels/index.ts` still does module-level `new ChannelService(OUTPUT_CHANNEL)` from utils-vscode. Consumers: only `languageServerOrphanHandler.ts` (`showChannelOutput`, `appendLine`). Migration path: use the existing `ChannelService` Effect.Service directly (no legacy shim) — see WI corrections.
3. **Drop utils-vscode from apex** — after 1+2, apex has no remaining utils-vscode import (only a stale test mock).

### WI corrections (supersede WI text)
- apex-replay-debugger **keeps** utils-vscode: still uses `TelemetryService`, `projectPaths`, `readFile`, `writeFile`, `createDirectory`, `errorToString`, `fileOrFolderExists` across index/adapter/commands/channels. WI claim "dep dropped from apex-replay" is false. apex-replay only repoints the conversion import.
- apex does NOT need a legacy `ChannelService` wrapper (unlike org's `setOrgChannel`/core's `setCoreChannel`, which exist only because their non-Effect callers still hold a utils-vscode `ChannelService`). apex's sole channel consumer (`languageServerOrphanHandler.ts`) already runs inside `Effect.fn` under the runtime built from `buildAllServicesLayer(context, nls.localize('channel_name'))` (`src/index.ts:31`), which merges `api.services.ChannelServiceLayer(pjson.displayName ?? 'Apex')` (`effect-ext-utils/src/allServicesLayer.ts:33-34`). So consume the `ChannelService` Effect.Service directly: `const channel = yield* api.services.ChannelService` then `yield* channel.showChannel` / `yield* channel.appendToChannel(text)`. No module-level `let`, no `setApexChannel`/`getApexChannelService` shim, no throw-if-unwired state, no wiring step in `index.ts`.
- No duplicate-channel risk: `ChannelService` is Cache-backed keyed by channel name (capacity 100, TTL infinity) in `salesforcedx-vscode-services/src/vscode/channelService.ts:41-71` (`ChannelServiceLayer` + `cache.get(channelName)`), so all resolutions of the 'Apex' name return the ONE `OutputChannel`. The plan's earlier dedupe worry is void.
- effect-ext-utils has no `vscode-uri` dep. Fn only calls `value.toString()`. Add type-only `import type { URI } from 'vscode-uri'` + `vscode-uri` in **`dependencies`** (NOT devDependencies): eslint `import/no-extraneous-dependencies` (`eslint.config.mjs:419-422`, `766-772`) only permits devDependencies under `**/test/**`,`**/__tests__/**`,`**/scripts/**` — a `src/` import from devDeps fails lint. apex + 17 other packages already list `vscode-uri` in `dependencies` (`salesforcedx-vscode-apex/package.json:39`). Type-only import is erased at runtime; add wireit compile dep.

### Out of scope
`apexLanguageClient.ts:80-111` `this.code2ProtocolConverter` = vscode-languageclient base-class member, unrelated. `visualforce startLanguageServer.ts` same base-class member. No change.

### Phase 3 — migrate apex ChannelService (consume Effect.Service directly)
No legacy shim, no `channels/index.ts` module state, no `index.ts` wiring. Consume `api.services.ChannelService` inside the Effect flow that already has the runtime/layer.
- `packages/salesforcedx-vscode-apex/src/languageServerOrphanHandler.ts`: drop `import { channelService } from './channels'`. The 3 call sites are plain (non-Effect) helpers — convert them to `Effect.fn`/gen so they can resolve the service. Each obtains it the same way the other helpers here do: `const channel = yield* (yield* ExtensionProviderService).getServicesApi.pipe(...)` → simpler: `const api = yield* (yield* ExtensionProviderService).getServicesApi; const channel = yield* api.services.ChannelService;` (`ExtensionProviderService` already imported, used at 73/166):
  - `showOrphansInChannel` (203) → Effect gen: resolve `channel`, then `yield* channel.showChannel; yield* channel.appendToChannel(advice); yield* channel.appendToChannel(''); yield* channel.appendToChannel(table)`. Called from `checkAndResolveOrphanedLanguageServers` (181) → `yield* showOrphansInChannel(x)`.
  - `showProcessTerminated` (242) / `showTerminationFailed` (246) → Effect gen resolving `channel` + `channel.appendToChannel(...)`. Called inside `killOne` (122,126) `Effect.tap`/`catchTag` bodies → return the Effect (tap/catch bodies already expect Effect).
  - Note `ChannelService.showChannel` = `channel.show()` and `appendToChannel` = best-effort `channel.appendLine` (never fails) — semantics match the old `showChannelOutput`/`appendLine`. `showChannelOutput()` old used `.show(true)` (preserveFocus); services `showChannel` uses `.show()` — acceptable (org/core migrations accepted same); note in PR.
- `packages/salesforcedx-vscode-apex/src/channels/index.ts`: delete file entirely (only exported `channelService` from utils-vscode; no other consumers after above). Confirm via grep no other importer of `./channels`.
- `packages/salesforcedx-vscode-apex/src/index.ts` `activateEffect`: eagerly resolve the channel at activation to preserve current behavior + make it discoverable. Old `channels/index.ts` created the 'Apex' channel eagerly at module load (`new ChannelService(OUTPUT_CHANNEL)`); the Cache-backed `ChannelService` creates it lazily on first `cache.get('Apex')`, and the orphan handler only writes when orphans exist — so without an eager resolve the 'Apex' channel would be absent from the Output dropdown after activation (regression) and the e2e dedupe count would be 0. Mirror core (`core/src/index.ts:70`): add `const channel = yield* (yield* api.services.ChannelService).getChannel; context.subscriptions.push(channel);` (`api` already bound at line 43). Runtime/layer already built at line 31.
- `test/jest/languageServerOrphanHandler.test.ts`: remove `jest.mock('../../src/channels', ...)` (18-23). Add `ChannelService` to the `makeApi` services stub (54-59), same shape as `TerminalService`/`PromptService`: `ChannelService: Effect.succeed({ showChannel: Effect.void, appendToChannel: () => Effect.void, getChannel: Effect.succeed(undefined), clearChannel: Effect.void })` (or jest.fn-wrapped variants to assert calls). `getServicesApi` (95, 246) already provides the whole `makeApi` object, so `yield* api.services.ChannelService` resolves against it. Assert on the stubbed `appendToChannel`/`showChannel` where the old test asserted on the `channelService` mock. Mirror in the isolated-module block (238-249).
- **e2e (Phase 3)**: add `packages/salesforcedx-vscode-apex/test/playwright/specs/apexOutputChannel.headless.spec.ts` (model: `salesforcedx-vscode-core/test/playwright/specs/coreOutputChannel.headless.spec.ts` — precedent for this exact migration, W-23348840, commit 2551bd4ca). Use `selectOutputChannel`, `countOutputChannelOptions`, `ensureOutputPanelOpen` from `@salesforce/playwright-vscode-ext`. `CHANNEL = 'Apex'` (= `channel_name` message, `i18n.ts:30`; also apex `displayName`).
