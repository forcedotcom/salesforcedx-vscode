# W-23355895 — Drop @salesforce/core from salesforcedx-apex-replay-debugger

## Context

- Goal: remove `@salesforce/core` from base DAP pkg `salesforcedx-apex-replay-debugger`. Prereq for web replay debugger.
- Core used in EXACTLY 1 file: `packages/salesforcedx-apex-replay-debugger/src/core/logContext.ts` — `fetchOverlayResultsForApexHeapDumps` (`ConfigAggregator.create` → `target-org`, `Org.create`, `connection.tooling.sobject('ApexExecutionOverlayResult').retrieve(id)`).
- Org = always workspace default (launch schema exposes only logFile/stopOnEntry/trace). == `ConnectionService.getConnection()`.
- Base pkg = separate node process (`program:./dist/apexReplayDebug.js`), spawned by host ext `salesforcedx-vscode-apex-replay-debugger`. No `vscode` import in base.
- Host already reads full log pre-launch (`debugConfigurationProvider.ts` → `config.logFileContents`); host already imports `breakpointUtil` from base pkg.
- Heap-dump ids: pure string scan (`scanLogForHeapDumpLines`, `|HEAP_DUMP|`, splitLine[3..6] = id/class/ns/line). Only overlay RESULT payload needs network; class/ns/line metadata stays in adapter.
- Match payload → `apexHeapDumps` by id via `heapDump.setOverlaySuccessResult` (`heapDump.ts`).
- Launch consumption: `apexReplayDebug.ts:129` gates on `scanLogForHeapDumpLines() && !(await fetchOverlay...)`.
- DO NOT reuse `COMPOSITE_BATCH_URL` (`constants.ts:11`) — hardcodes stale `v43.0`, and it's dead (only re-exported at `index.ts:15`, zero call sites). Build url dynamically from `conn.version` like `metadataDescribeService.runSObjectBatch` (`metadataDescribeService.ts:198`): request `url:'/composite/batch'`, subrequest `url:\`v${conn.version}/tooling/sobjects/ApexExecutionOverlayResult/${id}\``.
- REUSE existing batch idiom, don't invent a new one: `metadataDescribeService.ts:195-220,385-408` already solves composite/batch chunking with `Stream.grouped(MAX_SOBJECT_BATCH_SIZE=25)` + `Stream.mapEffect(..., {concurrency: BATCH_API_CONCURRENCY=15})` over `conn.request` POST `/composite/batch`. NO `Request`/`RequestResolver`/`makeBatched` (zero usages anywhere in repo — a novel mechanism for a solved problem).
- Host connection precedent: `checkpointService.ts:39` `getConnection` via `ExtensionProviderService.getServicesApi` → `ConnectionService.getConnection`.
- PRE-EXISTING BUG: fetch loop `return`s inside `for` (logContext.ts 251/258) → only FIRST heap dump fetched. Fixed by moving fetch host-side (batch over all ids).
- host has `salesforcedx-vscode-services` as devDep (line 47) — promote to dep.

### Phase 2 — host: resolve connection, batch-fetch overlay results, attach to config

commit: `feat(apex-replay-debugger): host-side heap-dump overlay batch fetch via ConnectionService - W-23355895`

- New host module (e.g. `.../services/heapDumpOverlayFetch.ts`): given `logFileContents` + connection, extract ids (import base `extractHeapDumpIdsFromLog`), batch-fetch → `HeapDumpResult[]`. Mirror `metadataDescribeService.runSObjectBatch` + the `describeCustomObjects` stream shape — do NOT hand-roll a second batching mechanism.
  - Dedup ids up front (plain `new Set`) before batching — repeated heap-dump ids in a log collapse to one subrequest.
  - `runOverlayBatch(ids: string[])`: build `{batchRequests: ids.map(id => ({method:'GET', url:\`v${conn.version}/tooling/sobjects/ApexExecutionOverlayResult/${id}\`}))}`, `conn.request` POST `/composite/batch` (dynamic version — NOT COMPOSITE_BATCH_URL), same headers as metadataDescribeService (`User-Agent`, `Sforce-Call-Options`).
  - `Stream.fromIterable(uniqueIds).pipe(Stream.grouped(25), Stream.mapEffect(batch => runOverlayBatch(Chunk.toArray(batch)).pipe(map subresponses → HeapDumpResult per id: statusCode 2xx → {heapDumpId, success: result}; else → {heapDumpId, error: <errorCode/message from batch error body>}), {concurrency: 15}), Stream.flattenIterables)` → `Stream.runCollect` → array. 25/15 match the existing MAX_SOBJECT_BATCH_SIZE / BATCH_API_CONCURRENCY constants (define local consts, or import a shared helper if one is extracted — see below).
  - Round trips: ceil(N/25) vs N (the pre-existing single-dump bug is fixed simply by batching ALL ids instead of `return`ing after the first).
  - CONSIDER: if the batch payload/headers/version logic is identical enough to `metadataDescribeService.runSObjectBatch`, extract a shared `compositeBatch(conn, subrequests)` helper in `salesforcedx-vscode-services` and consume it from both call sites rather than copying. Only diverge if the overlay retrieve response shape forces it.
- `debugConfigurationProvider.ts` `asyncDebugConfig`: after `logFileContents` set, resolve connection via `ConnectionService.getConnection()` (services api pattern from `checkpointService.ts`), run fetch, set `config.heapDumpResults`. On org-resolution failure attach single error marker (localized `unable_to_retrieve_org_info`) so adapter surfaces it — don't hard-throw (parity: today fetch failure is non-fatal, session still launches).
- `package.json`: promote `salesforcedx-vscode-services` devDep→dep.
- Files: `packages/salesforcedx-vscode-apex-replay-debugger/src/services/heapDumpOverlayFetch.ts` (new), `.../adapter/debugConfigurationProvider.ts`, `.../package.json`.
