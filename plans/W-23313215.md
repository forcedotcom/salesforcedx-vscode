# W-23313215 — Shrink soql bundle via effect ESM resolution

## Context

- Apply shared `effectEsmConditions` opt-in (`scripts/bundling/effect.mjs`, ADR 0021) to `packages/salesforcedx-vscode-soql/esbuild.config.mjs`, **effect-consuming desktop build only** (`dist/index.js`).
- Mirrors W-23313213 (org), W-23313212 (metadata), W-23293744 (reference format), W-23313205 (apex-replay-debugger — which likewise applied the override ONLY to its effect-consuming build and left the non-effect 2nd build untouched).
- `conditions: ['import','module','default']` → effect resolves to `dist/esm/*`; unused submodules (fast-check via `effect/Schema`) tree-shake out. Output stays CJS (from `nodeConfig.format`).
- soql esbuild: 4 builds — 2 desktop node (`dist/index.js` ext, `dist/server.js` LSP), 2 web. Web builds untouched (desktop-only, ADR 0021 opt-in scope).
- **`index.js` pulls effect** (`src/index.ts` imports `effect/Effect`, `effect/Scope`, `@salesforce/effect-ext-utils`; `commands/queryPlan.ts` imports `effect/Schema` → this is the fast-check pull the override tree-shakes; `lspClient/codeCompletion.ts` imports `effect/Effect`). This build gets the override.

### server.js is EXCLUDED — no effect, so override = pure blast radius, zero benefit

- `dist/server.js` bundles `@salesforce/soql-language-server/lib/server.js`. Dependency graph: zero effect — `grep -rl effect node_modules/@salesforce/soql-language-server/lib/` returns nothing; deps: `@salesforce/soql-common`, `antlr4-c3`, `antlr4ts`, `debounce`, `vscode-languageserver`, `vscode-languageserver-protocol`, `vscode-languageserver-textdocument` — no effect deps.
- no-effect graph + override = no shrink, still re-points other deps' resolution. Confirmed real change: `vscode-languageserver-textdocument` `exports["."]` = `{"browser":.../esm/main.js, "module":.../esm/main.js, "import":.../esm/main.js, "default":.../umd/main.js}` (no `node` key) — override flips resolved entry from `./lib/umd/main.js` to `./lib/esm/main.js`. (Other LSP deps have no `exports`/`module`, resolve via `main` → unaffected.)
- ADR 0021 rejected baking `conditions` into `nodeConfig` precisely because it "changes module resolution for EVERY dependency in a bundle, not just effect … could ship a broken ESM entry — unvalidated blast radius." no-effect bundle + override = same anti-pattern, no benefit.
- Decision: **do NOT spread `effectEsmConditions` into the server.js build.** Avoids the blast radius outright — no effect, no upside to validate. (If a future change adds effect to the LSP server, revisit with the full per-dep blast-radius table + `dist/server.js` byte capture + LSP runtime verification that apex-oas W-23313204 required.)
- Wireit `files` must list `effect.mjs` so cache invalidates on edit — both `vscode:bundle` + `vscode:bundle:local` (config imports it unconditionally, even though only one build consumes it).
