# W-23429481 — 15 Enforce zero-finding rules (grouped no-ops)

## Context

- Epic "Effect LS diagnostics: enforce in CI". WI #1 (W-23429440) shipped the ratchet: `scripts/effect-diagnostics.mjs` runs the LS CLI per Effect-adopting package and fails only on findings whose rule name is in `config/effect-diagnostics.json` `enforcedRules` (any severity). 13 enforced today (latest sibling: `returnEffectInGen`, W-23429477). `tsconfig.common.json` currently sets no `diagnosticSeverity`.
- **The WI's premise is wrong for 9 of its 11 candidates, and "0 findings today" is a false signal for 10 of them.** 10 of the 11 candidate rules ship `default: "off"` in `node_modules/@effect/language-service/schema.json` (`definitions.effectLanguageServicePluginDiagnosticSeverityDefinition.properties.<rule>.default`). An `off` rule emits nothing, so the ratchet — which filters *reported* diagnostics by name — sees 0 no matter how many real sites exist. Appending an `off` rule to `enforcedRules` alone is a guaranteed permanent no-op. Only `floatingEffect` defaults to `error`.
- Measured for real (LS 0.86.2): `npm run compile`, then temporarily set all 11 candidates to `"error"` in the `tsconfig.common.json` `@effect/language-service` plugin entry, ran `cli.js diagnostics --project <pkg>/tsconfig.json --format json` over the 19 discovered packages, tallied by rule name, reverted. - Second measurement, same method, on sibling rules the candidate set skipped: `globalRandomInEffect` **0**, `globalFetchInEffect` **0**, `globalTimersInEffect` **0**, `globalTimers` 7. The 3 zeros are in scope: enforcing `globalRandom` without `globalRandomInEffect` leaves `Math.random()` inside a gen unguarded, and `globalFetchInEffect`/`globalTimersInEffect` are free ratchets whose outside-Effect twins (4 / 7 findings) stay off. `packages/*/src` has 0 `Math.random` today, so these guards are purely forward-looking — the WI's "cannot regress" goal.
- ∴ enforce 5 rules: `floatingEffect`, `globalRandom`, `globalRandomInEffect`, `globalFetchInEffect`, `globalTimersInEffect`. Each needs **both** edits: `diagnosticSeverity: "error"` in `tsconfig.common.json` (makes an `off` rule report at all) **and** the name in `enforcedRules` (makes the gate fail on it). `floatingEffect` is already `error` by default; pin it explicitly so an upstream default change can't silently disarm it.
- `plugins` is not honored by plain `tsc` — `@effect/language-service` is installed as a dep with no tsc patch step (no patch script in `package.json`; `postinstall` is wireit). So `diagnosticSeverity` changes editor diagnostics + the CLI/ratchet, not `npm run compile` exit codes.
- Wireit already reacts: `check:effect-diagnostics` `files` lists both `tsconfig.common.json` and `config/effect-diagnostics.json`; `dependencies: ["compile"]` supplies the `out/*.d.ts` the CLI needs.
- All 32 `packages/*/tsconfig.json` extend `../../tsconfig.common.json` and none redeclare `plugins` — one edit covers every package.
- Overlap (WI's OVERLAP CHECK): honor the "enforcement is now automated" note **only for what is actually automated**. None of the 5 newly enforced rules maps to an existing `anti-patterns.md` FORBIDDEN section. The FORBIDDEN sections for `console.log`, `process.env`, `new Date()`/`Date.now()` and the matching Quick Reference `Logging`/`Config` rows stay unannotated judgment — claiming automation there would be false (78/43/47 live findings). New rows go in `references/diagnostics-findings.md`, the per-rule finding→fix table.
